This is the whole of the remaining critical path. Everything else in this
document is downstream of it.

The C was written against headers, not against diagnostics. The author compiled it on his own machine and fixed the errors that surfaced there.
executed.

### What to do with the failures

Work through them, but resist the temptation to delete a failing assertion. Each
one is either a real bug or a wrong expectation, and both are worth knowing
about. Several already were.

## 1. First real build

Once it compiles:

1. **`tools/stamp_digests.py`** hashes `libmagr_fortran.a` and writes the digest
   into each descriptor. Until this runs, every `binary.digest` stays `null` —
   which is correct, not an omission.
2. **`tests/fortran-conformance`** (33 tests) runs the numerical suite against
   the reference BLAS. The expected values were derived with an independent
   Python implementation rather than from a previous run, so they can fail.
3. **`tests/abi`** (20 tests) and **`tests/merkle-integrity/test_canonical.c`**
   (15 tests) and **`tests/merkle-integrity/test_sha256.c`** (6 tests).
4. **`tools/apply_license_headers.py --check`** stays green.

---

## 2. Get the C and Python Merkle implementations to agree

The Python reference (`42` tests passing) implements the same specification as
the C. Nothing yet asserts they produce identical digests.

Add `tests/merkle-integrity/fixtures/c_digest_fixture.json`, generated by the
Python reference, and have `test_canonical.c` assert against it. **This is the
highest-value test not yet written**, because until it exists "the canonical
encoding is deterministic" is a claim about one implementation agreeing with
itself.

## 3. Prove the Lean model

```bash
cd formal && lake build
```

Needs elan. Pinned at `leanprover/lean4:v4.19.0`.

Expect errors. The proofs were written without a typechecker, so
(a) `Rat` availability at that version, (b) the `calc` chains in `Axpy.lean`,
and (c) the `congr 1; ring` steps are the three things most likely to need work.
When it builds:

1. Re-run `tools/gen_proof_registry.py` — it will record `.olean` digests and set
   `build.status` from the actual outcome.
2. Re-run `tools/check_proof_registry.py`, which **refuses** an `.olean` digest
   while no toolchain is present. That check is the reason the registry can be
   trusted.

**Then read the disclaimer again.** A green `lake build` proves nothing about
`libmagr_blas.a`. The proofs are over ℚ; the runtime is binary64. See
[`merkle.md`](merkle.md) and `formal/MagrFormal/Disclaimer.lean`.

## 4. Chapel, Klong, Uiua

None is installed; all three adapters are source only.

- **Chapel** is the priority — it owns the scheduler, and the wavefront
  executor is already shaped to hand it a ready set via a task-launch callback.
  `magr_ir_execute_wavefronts` requires an explicit callback and reports how many
  nodes launched concurrently, so a `cobegin` adapter is a small, testable thing.
- **Klong and Uiua** string parsers accept only the documented patterns. Real
  frontends are substantial work; the typed lowerers work now.

---

## 5. Optimization — *after* a correct baseline

Not started, deliberately. Order matters:

1. **Baseline benchmarks first.** Throughput, latency, allocation volume, peak
   memory, scheduling overhead, language-boundary overhead, Merkle hashing
   overhead. Without a measured baseline, no optimisation has anything to be
   measured *against*.
2. **Caching**, keyed on input digests. Cache invalidation when semantic inputs
   change is already in the test plan.
3. **Fusion, with an equivalence contract first.** `axpy_fusion` is proved over
   ℚ and is **false over binary64** — `(α+β)·x` rounds once, `β·x + α·x` rounds
   twice. So fusion is a *tolerance-dependent* transformation and must be
   benchmarked for accuracy drift, not just speed. Do not silently substitute a
   fused operation for a verified one.
4. **SAC** only after the above, and only where a proven equivalence contract
   exists between what SAC emits and what the IR means.

### The performance claim that must not be made

This repository vendors **reference** BLAS. It is written for clarity and
portability, not speed. Beating OpenBLAS, MKL, or cuBLAS with it is not a goal,
and any such claim in a README should be treated as a benchmark error until
demonstrated on the same hardware with the same workloads.

## 6. Things not yet built, named so they are not discovered later

- **Transparency log / external root publication.** A root stored in the structure
  it protects is not a commitment to it. See [`merkle.md`](merkle.md).
- **Ed25519.** Compiles out to `MAGR_STATUS_UNSUPPORTED`. Deliberate: a
  half-managed key is worse than an obviously-unauthenticated root.
- **Triangular solves with general singularity detection.** `DTRSV`/`DTRSM` detect
  only an all-zero diagonal. A matrix that is singular for some right-hand side
  with a nonzero diagonal is not caught, and the descriptors say so rather than
  overstating the guarantee.
- **Single-precision and complex functors.** The double-precision ABI is
  designed to extend but is not yet extended.
- **Rank-different broadcasting.** Refused. Front ends insert an explicit reshape.
- **`view.slice` lowering.** Declared in the IR, not implemented. Both adapters
  say so rather than quietly returning a wrong shape.
- **Per-axis reduction.** v1 reduces to a scalar. Slice + transpose + full
  reduction is the documented workaround, which keeps reduction order fixed.
- **XERBLA tripwire on non-GNU toolchains.** Reads a private counter that nothing
  increments, and `magr_blas_xerbla_interposed()` reports `0` so a caller can tell
  the difference instead of being handed a false all-clear.

## Definition of done

Per the specification, ten items. Today: **two** are partially complete — the
canonical execution manifest design (no run has produced one) and Merkle root
construction with tamper detection (implemented and tested in one language, not
yet in the C tree or in a running program).

The other eight all require a compiler.
